20// Forward-dependency enumeration.

22// Returns the UUIDs that the given asset directly references. Designed as a

24// template) so that:

38//------------------------------------------------------------------------------
39// prefab -> the prefabs instanced inside it.
40//
41// A prefab is stored as an opaque serialized buffer, so unlike the other types
42// there is no loaded object to interrogate. Rather than deserialize it into a
43// scratch registry - which would need an asset_manager, run component
44// constructors and resolve every unrelated asset reference on the way - this
45// reads the references straight out of the buffer, which is JSON: every
46// `prefab_component` in it carries a `source` whose `uid` is the asset it
47// instances.
48//
49// Covers scene_prefab too, which is the same format under a different name.
50//
51// Returns direct references only, in document order, deduplicated. Nil uids and
52// anything unparseable are skipped, so a damaged buffer yields fewer references
53// rather than throwing.
54//------------------------------------------------------------------------------
55ENGINE_EXPORT auto get_referenced_uids(const prefab& p) -> std::vector<hpp::uuid>;

57//------------------------------------------------------------------------------
58// Reverse-dependency lookup over the currently-loaded asset set.
59//
60// Walks every renderable-asset container registered with `am` (materials,
61// meshes) and returns the UUIDs of those whose `get_referenced_uids`
62// contains `uid`.
63//
64// Note: `model` is intentionally absent — it isn't a top-level asset_manager
65// storage type, it lives inside model_component on prefabs/scenes. Prefab
66// thumbnails are handled separately via the mass-invalidation path in
67// `cascade_thumbnail_regen`.
68//
69// This intentionally inspects only assets that are *already in memory*
70// (`asset_handle::peek()` — no forced loads, no deferred-task submission).
71// Unloaded dependents are correctly handled by the editor's lazy thumbnail
72// regeneration: they'll re-render against the new dependency content the next
73// time their thumbnail is requested.
74//
75// Cost: O(N_loaded × N_deps_per_asset). N is bounded by what the editor
76// actually has open, so this is cheap in practice.
77//------------------------------------------------------------------------------
78ENGINE_EXPORT auto find_loaded_dependents(asset_manager& am,
79 const hpp::uuid& uid) -> std::vector<hpp::uuid>;

81//------------------------------------------------------------------------------
82// Same as `find_loaded_dependents` but follows the chain transitively: returns

121//------------------------------------------------------------------------------
122// Topologically orders `roots` and everything reachable from them.
123//
124// Takes the dependency lookup as a callback rather than an asset_manager: the
125// ordering is pure graph work, and keeping it that way lets it be tested against
126// synthetic graphs instead of a live asset database. The caller supplies both the
